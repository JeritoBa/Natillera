# Business Rules Catalogue

Single source of truth for the business rules of the Natillera system. Each rule has a **stable ID** that must never be reused or renumbered. If a rule is retired, keep its row and mark it `Retired`.

**How to use it**

- Before implementing a feature or changing behavior, add or update the rule here first (see [AGENTS.md](../AGENTS.md#spec-driven-development) and [specs/README.md](specs/README.md)).
- Specs in [`docs/specs`](specs/README.md) reference rules by ID.
- Tests should mention the rule ID in the test name or in a comment when practical (e.g. `// MP-04`).
- Status values: `Implemented`, `Partial` (enforced but with a gap noted), `Pending` (planned, not enforced), `Open question` (owner decision needed).

**Conventions used in the "Enforced in" column** (paths relative to `Natillera.Backend/`): `Domain/...` entities, `Application/...` services, `Infrastructure/...` EF/repositories, `Presentation/...` controllers, `Program.cs`. Frontend paths are relative to `Natillera.Frontend/src/`.

**Test references.** Backend tests live in `Natillera.Backend.Tests` (xUnit + in-memory fakes, no DB): `Domain/*Tests.cs` and `Application/*ServiceTests.cs`. Frontend tests are Vitest `*.test.ts`. "None" means no automated test exists today. Anything that depends on EF/Postgres behavior (repositories, unique indexes, migrations, controllers, JWT middleware) has **no automated test yet** (integration tests are pending).

## FIN - Financial integrity (cross-cutting)

| ID | Rule | Rationale | Enforced in | Tests | Status |
|---|---|---|---|---|---|
| FIN-01 | Money is always `decimal` (never float/double). Amounts persist as `numeric(18,2)`; the loan interest rate as `numeric(9,4)`. | Floating point cannot represent money exactly. | All entities; `Infrastructure/Persistence/Configurations/*` (`HasPrecision`) | Implicit in all domain tests | Implemented |
| FIN-02 | A `Transaction` amount is always greater than zero; direction (Income/Expense) carries the sign. Description is required, max 200 chars. | Controlled type/direction; no ambiguous signed amounts. | `Domain/Entities/Transaction.cs` | `TransactionTests.Constructor_NonPositiveAmount_Throws`, `Constructor_BlankDescription_Throws`, `Constructor_DescriptionOver200_Throws` | Implemented |
| FIN-03 | Every business entity that moves money (monthly payment, loan, loan payment, loan interest/`Performance`, activity, activity assignment) has **at most one** `Transaction` (1:1, unique index on each `TransactionId`). A `Transaction` is never edited directly: it mirrors its entity and is only updated/cancelled by the service that updates/cancels the entity. | One source of truth per movement; traceability. | `Infrastructure/Persistence/Configurations/*Configuration.cs` (unique `TransactionId`); services in `Application/*` | Service tests assert the transaction created/updated/cancelled with the entity (e.g. `LoanServiceTests.UpdatePaymentAsync_IncreaseWithinPrincipal_UpdatesPaymentAndTransaction`); unique index: None | Implemented |
| FIN-04 | Transaction type and direction are fixed per source: MonthlyPayment = Income; Loan = Expense; LoanPayment = Income; Performance (loan interest) = Income; Activity = Expense; ActivitySale (paid assignment) = Income. | Balance depends on direction being controlled. | `Application/MonthlyPayments/MonthlyPaymentService.cs`, `Loans/LoanService.cs`, `Activities/ActivityService.cs` | Asserted in the service tests of each module | Implemented |
| FIN-05 | Every create, update and cancel of a business entity writes **exactly one** `Log` (old value -> new value, user from the JWT) in the **same Unit of Work** (single DB transaction) as the entity and its `Transaction`. If any part fails, nothing is saved. | Auditability and atomicity. | `Application/Common/IUnitOfWork.cs`, `Infrastructure/Persistence/EfUnitOfWork.cs`, every financial service | Log assertions in `MonthlyPaymentServiceTests` (e.g. `CreateAsync_Pending_DoesNotCreateTransactionAndWritesOneCreateLog`, `CancelAsync_Paid_..._WritesDeleteLog`), `LoanServiceTests`, `ActivityServiceTests`; real rollback against Postgres: None | Implemented (rollback unit-tested only with fakes) |
| FIN-06 | "Delete" never physically deletes. Cancelling sets the entity status to `Cancelled` and its live `Transaction` gets `IsCancelled = true`. Cancelled transactions are excluded from every balance/total. The `Log` action used for cancellation is `Delete`. | Financial records are never silently deleted. | Domain `Cancel()` methods; `Transaction.Cancel()`; `Infrastructure/Persistence/Repositories/DashboardRepository.cs` | `TransactionTests.Cancel_Active_SetsIsCancelled`; `Cancel_*` tests per entity | Implemented |
| FIN-07 | A cancelled record is terminal: it cannot be modified, and cancelling twice is an error. Applies to Transaction, MonthlyPayment, Loan, LoanPayment, Performance, Activity, ActivityAssignment. | Prevents rewriting history. | `Domain/Entities/*.cs` (`Cancel`, `UpdateDetails`/`Update`) | `Cancel_Twice_Throws`, `UpdateDetails_Cancelled_Throws`, `Update_AfterCancel_Throws` (per entity test class) | Implemented |
| FIN-08 | **Pending items have no `Transaction`** (monthly payment, loan interest/`Performance`, activity assignment). The Income `Transaction` is created at the moment the item is marked **Paid**. `Paid -> Pending` is never allowed. Loans, loan payments and activities always have their `Transaction` from creation. | Money only counts when it actually moved. | `MarkAsPaid` in `Domain/Entities/{MonthlyPayment,Performance,ActivityAssignment}.cs`; services | `MonthlyPaymentServiceTests.UpdateAsync_PaidToPending_Throws`, `LoanServiceTests.UpdateInterestAsync_PaidToPending_Throws`, `ActivityServiceTests.UpdateAssignmentAsync_PaidToPending_Throws`, plus `*_Pending_CreatesNoTransaction` tests | Implemented |
| FIN-09 | Balances are **derived** from non-cancelled transactions (`available money = SUM(Income) - SUM(Expense)`); no balance is stored or editable. | Single source of truth. | `Infrastructure/Persistence/Repositories/DashboardRepository.cs` | None (repository, needs integration test) | Implemented |
| FIN-10 | `Log` records are immutable (no update operations) and require a user, an entity id, and defined entity-type/action enums. | Audit trail integrity. | `Domain/Entities/Log.cs` | `LogTests.Constructor_*` | Implemented |
| FIN-11 | Optimistic concurrency (`RowVersion`) on financial entities to avoid lost updates from concurrent edits. | Two admin sessions could overwrite each other. | Not implemented | None | **Pending** |
| FIN-12 | Persisted enums are stored as strings (e.g. `'Pending'`, `'Cancelled'`); the API serializes enums as strings. | Readable data, safe against reordering. | `Infrastructure/Persistence/Configurations/*` (`HasConversion<string>`), `Program.cs` (`JsonStringEnumConverter`) | None | Implemented |
| FIN-13 | **Available money check.** A create or edit that reduces the available money (create/edit loan or activity increasing its expense; lowering the amount of a Paid monthly payment, a loan payment or a Paid loan interest) is rejected when the outflow is greater than the available money (DASH-01, computed before the change). Reaching exactly 0 is allowed. Cancellations are exempt. The check runs inside the same Unit of Work; a rejection saves nothing. Concurrent operations are not protected yet (see FIN-11). | The cash must never go negative because of a new movement. | `Application/Transactions/CashGuard.cs`; `LoanService` (create/update loan, update payment, update interest), `ActivityService` (create/update), `MonthlyPaymentService.UpdateAsync`; `TransactionRepository.GetAvailableMoneyAsync` | `CashGuardTests`; `*ServiceTests` (`*_FIN13`) | Implemented (backend; frontend pending) |
