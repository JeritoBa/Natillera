# Natillera - Business Process Flow Diagrams

## Purpose

These flow diagrams represent the main business processes of the Natillera system.

They focus on **what happens in the business**, not on software classes, controllers, repositories, or database implementation details.

Updated to the current implementation. Rules are cataloged by ID in docs/business-rules.md; features are specified in docs/specs.

Conventions that apply to EVERY flow below:

* Only the Admin performs mutations; Members are read-only (AUTH-01).
* Each create / update / cancel of a business entity, its Transaction (when it has one) and its Log entry are saved together in one database transaction. If any part fails nothing is saved (FIN-05).
* "Cancel" never deletes: the entity becomes CANCELLED and its live Transaction is flagged cancelled, so it no longer counts in any balance (FIN-06). A cancelled record cannot be modified or cancelled again (FIN-07).
* Pending items (monthly payment, loan interest, activity assignment) have NO Transaction. The INCOME Transaction is created when the item is marked PAID, and PAID never goes back to PENDING (FIN-08).

# 1. Register and Pay a Monthly Payment

## Business objective

Register a member's monthly contribution (pending or paid) and record the corresponding financial movement only when the money is received.

## Flow

```text
START
  ↓
Admin selects member, year, month, amount
and the initial status (PENDING or PAID)
  ↓
Is the member active?
  ├── NO → Reject → END
  │
  └── YES
        ↓
   Is the amount >= the configured minimum?
   ├── NO → Reject → END
   │
   └── YES
         ↓
      Does a NON-CANCELLED payment already exist
      for this member + year + month?
      ├── YES → Reject duplicate (conflict) → END
      │
      └── NO
            ↓
         Create MonthlyPayment
            ↓
         Initial status?
         ├── PENDING → no Transaction yet
         │              ↓
         │           Write Log (create) → END
         │
         └── PAID → Create Transaction
                     Direction = INCOME
                     Type = MONTHLY_PAYMENT
                     Link it and set PaidAt
                     ↓
                  Write Log (create) → END
```

## Mark a pending payment as paid (edit)

```text
Admin edits a PENDING payment and sets status PAID
  ↓
Does it already have a live (non-cancelled) Transaction?
  ├── YES → reuse and update it
  ├── CANCELLED Transaction → Reject (it cannot be reused) → END
  └── NONE → create INCOME Transaction (MONTHLY_PAYMENT)
  ↓
Set status PAID + PaidAt, write Log (update) → END
```

Editing a PAID payment updates its amount and Transaction; setting it back to PENDING is rejected.

## Cancel ("Anular")

```text
Admin cancels a PENDING or PAID payment
  ↓
Already cancelled? ── YES → Reject → END
  ↓ NO
Status = CANCELLED, cancel its live Transaction (if any)
  ↓
Write Log (delete) → END
```

After cancelling, the same member/period can be registered again.

## Important business rules

* MP-01 .. MP-09 and MEM-07 (see business-rules.md).
* Members only see PAID payments; the Admin sees every status.
* A member's PENDING payments are the "pending payments" notice shown on the dashboard and block the member's deactivation.

# 2. Create Loan

## Business objective

Create a loan for an active member and register the money disbursement made by the Natillera.

## Flow

```text
START
  ↓
Admin enters borrower, principal amount,
interest rate and start date
  ↓
Is the borrower an active member?
  ├── NO → Reject → END
  │
  └── YES
        ↓
     Is amount > 0 and interest rate >= 0?
     ├── NO → Reject → END
     │
     └── YES
           ↓
        Create Loan (status ACTIVE)
           ↓
        Register financial Transaction
        Direction = EXPENSE
        Type = LOAN
           ↓
        Write Log (create)
           ↓
          END
```

## Edit or cancel a loan

```text
Admin edits or cancels a loan
  ↓
Is the loan cancelled? ── YES → Reject → END
  ↓ NO
Does it have any NON-CANCELLED payment or interest?
  ├── YES → Reject (cancel those first) → END
  │
  └── NO
        ↓
     Edit → update loan and its Transaction amount
     Cancel → loan = CANCELLED, cancel its Transaction
        ↓
     Write Log (update / delete) → END
```

## Important business rules

* LOAN-01, LOAN-07, MEM-07.
* There is no member loan request or approval step: the Admin creates loans directly.
* A member cannot be deactivated while having an ACTIVE loan.

# 3. Make Loan Payment (principal)

## Business objective

Register a payment made by a borrower toward the principal of an existing loan and update the loan's financial state.

## Flow

```text
START
  ↓
Admin selects the loan and enters amount + payment method (CASH or TRANSFER)
  ↓
Does the loan exist and is it not cancelled?
  ├── NO → Reject → END
  │
  └── YES
        ↓
     Outstanding principal =
       initial amount - sum of non-cancelled payments
        ↓
     Is amount > 0 and <= outstanding principal?
     ├── NO → Reject (a payment can never exceed the principal) → END
     │
     └── YES
           ↓
        Create LoanPayment (PAID)
           ↓
        Register financial Transaction
        Direction = INCOME
        Type = LOAN_PAYMENT
           ↓
        Refresh loan status:
          outstanding principal = 0 AND no PENDING interest
            ├── YES → loan = PAID (set end date)
            └── NO  → loan = ACTIVE
           ↓
        Write Log (create) → END
```

Editing a payment is allowed up to (outstanding principal + its previous amount) and updates its Transaction. Cancelling a payment cancels its Transaction, refreshes the loan status (a PAID loan returns to ACTIVE and its end date is cleared) and writes a Log.

## Important business rules

* LOAN-02 .. LOAN-06.
* "Total por pagar" = outstanding principal + pending interest (LOAN-08).

# 4. Create and Assign Activity

## Business objective

Create an activity financed by Natillera resources, assign quantities of units to members, and record the income when each assignment is paid.

## Flow: create / edit / cancel the activity

```text
START
  ↓
Admin enters name, description, quantity,
unit cost, unit sale price, start date
  ↓
Are quantity, cost and price > 0 AND price >= cost?
  ├── NO → Reject → END
  │
  └── YES
        ↓
     Create Activity (status PENDING)
        ↓
     Register Transaction
     Direction = EXPENSE, Type = ACTIVITY
     Amount = quantity x unit cost
        ↓
     Write Log (create) → END
```

* Editing updates the activity and its EXPENSE amount. Quantity cannot go below the assigned quantity, and the sale price cannot change once an assignment is PAID.
* Cancelling is rejected while the activity has non-cancelled assignments; otherwise the activity and its EXPENSE Transaction are cancelled.

## Flow: assign units to a member

```text
Admin selects activity, member and quantity
  ↓
Is the activity cancelled? ── YES → Reject → END
  ↓ NO
Is the member active? ── NO → Reject → END
  ↓ YES
Does the member already have a NON-CANCELLED assignment in this activity?
  ├── YES → Reject → END
  │
  └── NO
        ↓
     Is 0 < quantity <= available units?
     ├── NO → Reject → END
     │
     └── YES
           ↓
        Create ActivityAssignment (PENDING, no Transaction)
           ↓
        Refresh activity status → Write Log (create) → END
```

## Flow: collect an assignment

```text
Admin marks a PENDING assignment as PAID
(quantity can only be edited while PENDING)
  ↓
Register Transaction
Direction = INCOME, Type = ACTIVITY_SALE
Amount = quantity assigned x unit sale price
  ↓
Assignment = PAID (PaidAt set)
  ↓
Refresh activity status:
  all units assigned AND all non-cancelled assignments PAID → FINISHED ("Cerrada")
  otherwise → PENDING
  ↓
Write Log (update) → END
```

Cancelling an assignment (PENDING or PAID) cancels its Transaction if it was paid, refreshes the activity status (a FINISHED activity returns to PENDING) and writes a Log.

## Important business rules

* ACT-01 .. ACT-12.
* The assignment is the sale record; there is no separate ActivitySale entity.
* A member cannot be deactivated with PENDING assignments.

# 5. Register Financial Transaction

## Business objective

Record an actual financial movement generated by a business operation.

## Flow

```text
START
  ↓
A business operation (see flows 1-4 and 6) generates a movement
  ↓
Determine amount (> 0) and direction
  - INCOME  = money enters the Natillera
  - EXPENSE = money leaves the Natillera
  ↓
Determine transaction type
  - MONTHLY_PAYMENT (income)
  - LOAN (expense)
  - LOAN_PAYMENT (income)
  - PERFORMANCE = loan interest (income)
  - ACTIVITY (expense)
  - ACTIVITY_SALE (income)
  ↓
Create Transaction inside the SAME database transaction
as the originating entity and its Log
  ↓
END
```

## Important business rules

* A Transaction is created and changed only by the operation that owns it; there is no endpoint to create or edit one directly.
* Each business entity has at most one Transaction (1:1); pending items have none yet.
* Cancelled Transactions stay visible but are excluded from every balance.
* Available money = sum of INCOME - sum of EXPENSE of non-cancelled Transactions; it is derived, never stored.

# 6. Register and Pay Loan Interest (Performance)

## Business objective

Represent the interest generated by a loan and record the income when it is collected. Interest is entered manually by the Admin; it is not generated automatically.

## Flow

```text
START
  ↓
Admin enters interest amount (> 0), description
and status PENDING or PAID for an existing, non-cancelled loan
  ↓
Status?
  ├── PENDING → create Performance, no Transaction
  └── PAID → create Performance + Transaction
              Direction = INCOME
              Type = PERFORMANCE
  ↓
Refresh loan status (pending interest keeps the loan ACTIVE)
  ↓
Write Log (create) → END
```

## Mark pending interest as paid / cancel

```text
Admin edits PENDING interest and sets status PAID
  ↓
Create INCOME Transaction (PERFORMANCE), set PaidAt
  ↓
Refresh loan status, write Log (update) → END

PAID → PENDING is rejected.

Cancel: interest = CANCELLED; if it was PAID its Transaction is cancelled;
refresh loan status; write Log (delete).
```

## Important business rules

* LOAN-05, LOAN-06, FIN-08.
* Paid interest is shared equally among active members (rounded to 2 decimals) in each member's savings (DASH-06).
* Open question LOAN-10: interest rounding mode.

# 7. Deactivate a Member

## Business objective

Remove a member from active participation without losing history, only when they owe nothing.

## Flow

```text
START
  ↓
Admin deactivates a member
  ↓
Does the member have any of:
  - PENDING monthly payments
  - ACTIVE loans
  - PENDING loan interest
  - PENDING activity assignments
  ├── YES → Reject, listing the counts per kind → END
  │
  └── NO
        ↓
     is_active = false
        ↓
     The member can no longer log in and any open session
     stops working on its next request (token rejected, HTTP 401)
        ↓
       END
```

Activating a member is always allowed. Member changes do not write Log entries today (open question MEM-08).

# 8. Login and Session

## Flow

```text
START
  ↓
User submits email + password
  ↓
Valid credentials?
  ├── NO → generic "invalid email or password" → END
  │
  └── YES
        ↓
     Is the user active?
     ├── NO → "inactive user" → END
     │
     └── YES → issue JWT (role Admin or Member) → dashboard
  ↓
Every later request: token valid AND user still active?
  ├── NO → HTTP 401 → frontend logs out and shows
  │        "Tu sesión ya no es válida. Inicia sesión de nuevo."
  └── YES → continue
```

# Diagram Relationship Overview

Every financial operation follows the same shape; the entity decides when the Transaction exists.

```text
 Monthly payment (PENDING → PAID) ─┐
 Loan interest   (PENDING → PAID) ─┼─→ INCOME Transaction created when marked PAID
 Activity assignment (PENDING → PAID)┘

 Loan payment ───────────────────────→ INCOME Transaction created with the payment
 Create Loan ────────────────────────→ EXPENSE Transaction created with the loan
 Create Activity ────────────────────→ EXPENSE Transaction created with the activity

 Any create / update / cancel ───────→ one Log entry (same database transaction)
 Any cancel ─────────────────────────→ entity CANCELLED + live Transaction cancelled

 Transactions (non-cancelled) ───────→ Available money (derived)
 Available money + lent + activities → Total natillera balance (dashboard, derived)
```
